# Five-screen demonstration and acceptance

The actual Chromium workflow is [recorded here](../integration/urban-validation.json), with the tested commit and run URL. It covers the connected API/SQLite app and a separate browser sandbox. Earlier browser-launch blockers applied to the old local environment, not this executed CI check.

1. Open the app using the [run instructions](../README.md). Confirm the connection mode and demonstration label.
2. On Overview, distinguish synthetic cluster metrics from the separate official listing cards. High priority means a rankable score at least 60 under current weights, an illustrative cutoff.
3. Explore US-A, inspect source dates and change the deficit filter. US-E has missing inputs and remains unranked under the default weights.
4. Prioritize Needs shows US-A at 65.0. Change weights, inspect each contribution and export the priority report.
5. Compare in-place improvement and redevelopment. Edit assumptions. Relocation requires explicit opt-in and a reason. In server mode wait for the Python consistency check.
6. Draft a service work, start it and mark physical completion. Verified-service counts must not increase automatically.
7. Attach a harmless consented demonstration file. Use a different reviewer name, a fresh observation and a measurement meeting the target. Typed names are not authenticated independence.
8. Record a resident issue. Verification becomes disputed. A response alone does not restore it; attach fresh evidence and review again.
9. Export the brief. Check assumptions and evidence metadata; it must not contain file base64 or the officer key.

Automated layout checks cover 1440, 768 and 375 pixels across all screens, but do not replace keyboard/screen-reader and real-user evaluation. The mobile check waits for the drawer to close before screenshots. OSM tiles are disabled in CI. Public-data access and field validation are separate from browser correctness.
